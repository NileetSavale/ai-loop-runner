When Tests Lie

A coding agent writes a fix, runs the repository's tests, and stops when they pass. SWE-bench then checks the fix against hidden tests the agent never saw. This page follows real bugs through cheap models, strong models, cascades and reviewers, and shows how often passing the tests does not mean the fix is right, and what that costs.

    The problem, in four steps

    Coding agents grade their own work with the project's tests, and cost-saving setups trust that grade. This study measures how often the grade is wrong and what that does to them.

    1 · How agents work

    The agent checks its own fix

    It reads the bug report, edits the code, runs the project's existing tests, and tries again until they pass. Passing tests means "done".

    2 · How teams save money

    Cheap model first, strong model if needed

    A cascade lets a cheap model (Claude Haiku) try first. Only if its fix fails the tests is the bug handed to a strong model (Claude Sonnet), which costs about 14 times as much per bug.

    3 · The catch

    Tests can pass when the fix is wrong

    The project's tests were written before the bug was reported, so they often don't exercise it. SWE-bench keeps hidden tests, written with the real fix, that the agent never sees. We use them as the answer key.

    4 · The consequence

    The cascade never sees those failures

    A wrong fix that passes the tests is accepted and never escalated. The cascade pays for the strong model on the failures it can see, and ships the ones it can't.

    A real example · django-13794

    The bug report: Django's add template filter gives an empty string when you add a normal string and a lazy (translatable) string.

    The cheap model's fix (simplified): teach the lazy string to be added to a normal one. 
    class __proxy__:
+   def __radd__(self, other):
+       return other + str(self)
    ✓ Project's tests pass → fix accepted
    The hidden test also adds two lazy strings, which needs the twin method the fix never wrote. 
    "text" + lazy   # works now
lazy + lazy     # still fails: no __add__
    ✗ Hidden test fails → wrong, and nobody noticed
    Why it matters: how the cheap models fail (436 fresh bugs)

    QUESTION 1How often do the tests lie?
    22% of the fixes Haiku's loop accepted fail the hidden tests (32% for Flash-Lite, 15% even for Sonnet). Most often the hidden test checks a detail the bug report never states (47%), or the fix misses a twin code path, as above (28%).
    QUESTION 2Does "cheap first, escalate on failing tests" help?
    Not for Haiku: 331 bugs solved against 330 for Haiku alone, at 5.7× the cost. It helps only when the cheap model's failures are mostly visible: in the pilot, Flash-Lite's cascade went from 16 to 24 of 41 bugs.
    QUESTION 3Can a reviewer catch the lies?
    Having the strong model read the cheap model's passing fix before accepting it lifts the cascade to 361 against Sonnet's 365 (a difference within noise). It catches 80–93% of wrong fixes but also rejects 21–36% of good ones, so 36% of bugs escalate and it costs 7% more than Sonnet alone. It would save money below 32% escalation.
    QUESTION 4Does it help to know which tests were already broken?
    On the 47 bugs whose tests fail before the agent changes anything, telling those failures apart from the agent's own cut the cost per bug 2.5× ($0.072 against $0.183) and resolved 37 bugs against 32.

    When does a reviewed cascade pay off?

    A cheap model tries first. If its fix passes the tests, a reviewer reads it; a rejected fix, or one that never passes, goes to the strong model. Move the sliders to see when that beats running the strong model on everything. Start from a measured setup, then change one thing at a time.

    How good are the reviewers?

    Each reviewer read fixes that had already passed the repository's tests, then approved or rejected them. The hidden tests say which fixes were actually right.

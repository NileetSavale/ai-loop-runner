# Failure attribution for LLM coding agents: caused-by-me vs pre-existing, flaky, environment, or stale-test failures

Research conducted 2026-11-06. About 16 search/fetch calls. Status labels: **[preprint]** = arXiv only, no venue confirmed on the page; **[peer-reviewed]** = venue confirmed by the source; **[blog/vendor]** = non-refereed. Where a label comes from my memory and not a fetched page, it says so.

## Q1. Which agent systems run tests before changing anything (a baseline) and compare failures before and after? How?

### Takeaway
Agentless is the only agent system I could confirm, from its primary paper, that does an explicit before/after comparison. It runs the full existing suite on the unmodified repo, keeps only tests that pass, asks the LLM to drop tests the fix might legitimately change, and ranks candidate patches by how many of those baseline-passing tests they break. For SWE-agent, OpenHands, AutoCodeRover, CodeR, Moatless, Aider and the commercial agents, I found no primary-source description of a baseline-diff step in the searches I ran.

### Cited Findings
- **Agentless (Xia et al.), arXiv 2407.01489v2, 29 Oct 2024 [preprint per the fetched page; see Gaps on venue].** Section 3.3.2: Agentless "runs all the existing tests in the repository to identify a set of passing tests" on the original codebase. It then gives that list to the LLM and asks it to "identify any tests that should not be ran to check if the issue has been correctly fixed", glossed as "the tests that may be updated/patched during issue fixing". The tests that remain form the regression suite. — [Agentless HTML v2](https://arxiv.org/html/2407.01489v2)
- Agentless "keeps the patches with the lowest number of regression failures". It then runs the survivors against its generated reproduction test, keeps only patches that print "Issue resolved", and if none do it will "fall back on only using the regression test results for selection". — [Agentless HTML v2](https://arxiv.org/html/2407.01489v2)
- Agentless states: "We do not directly use the provided list of regression tests". It derives its own baseline and does not use SWE-bench's PASS_TO_PASS. The same paper has a stricter wording elsewhere (§5.1.3: it "will remove a patch if it cannot pass the regression tests"), and the paper does not reconcile the two. — [Agentless HTML v2](https://arxiv.org/html/2407.01489v2)
- **Engineering Agent (Meta-style "agentic program repair from test failures at scale"), arXiv 2507.18755, Jul 2025 [preprint].** Adds a step that confirms the target test reliably fails before the repair loop starts. This verifies the target failure. It does not separate out unrelated failures. — [arXiv 2507.18755](https://arxiv.org/html/2507.18755v1) (search-snippet level; not fetched in full)
- **TDAD (Alonso, Yovine, Braberman), arXiv 2603.17973, 18–19 Mar 2026 [preprint; submitted to ACM AIWare 2026 Data & Benchmark track, acceptance not stated].** Builds a code→test dependency graph so the agent knows which existing tests to run before committing a patch. On SWE-bench Verified with Qwen3-Coder 30B (100 instances), regressions fell from 6.08% to 1.82%. Generic "do TDD" instructions without targeted test context raised regressions to 9.94%. The abstract page does not say whether it takes a pre-change baseline. — [TDAD abstract](https://arxiv.org/abs/2603.17973)
- **OpenHands:** a cost analysis says OpenHands spends many tokens on "execution of numerous reproduction and regression tests". This describes behaviour, not a formal baseline-diff gate. — [SWE-Effi, arXiv 2509.09853](https://arxiv.org/pdf/2509.09853) (snippet)
- **"Breaking, Stale, or Missing?" (2026), see Q4:** the prompt for its evaluated agents (Claude Code, Codex CLI, etc.) lets them stop when "remaining failures are clearly unrelated to the current commit". The attribution is left to the agent's judgement and is not measured. — [arXiv 2605.06125](https://arxiv.org/html/2605.06125v1)
- **Harness level:** the SWE-bench harness does execute PASS_TO_PASS, but "results are not surfaced in leader-board rankings", so regression behaviour is reported only incidentally. — [TDAD PDF](https://arxiv.org/pdf/2603.17973) (snippet)

### Inferences
- Agentless's design is the closest published analogue to "name already-failing tests before the first attempt". It defines regressions relative to an observed baseline (passing on the original repo), not relative to the benchmark's metadata. It also adds an LLM judgement step for tests expected to change, which covers the stale-test case. That step is unvalidated: the paper reports no accuracy figure for the LLM's test-exclusion choices.
- Agentless counts regressions as *baseline-passing → now failing*. Tests already failing at baseline are excluded by construction, so pre-existing failures cannot penalise a patch. Flakiness among baseline-passing tests is not handled: there is no mention of reruns.

### Gaps
- No primary source fetched for SWE-agent, AutoCodeRover, CodeR, Moatless Tools, Aider, Devin, Cursor, Claude Code or Codex describing an explicit pre-change baseline run with a before/after diff. AutoCodeRover's paper (arXiv 2404.05427) surfaced, but the snippet described only context retrieval and specification inference. CodeR did not appear in results at all. This is a gap in what I fetched, not evidence that these systems lack the behaviour. Checking their repos and prompts directly is the next step.
- Agentless venue: from memory I believe it was published at FSE 2025, but the fetched arXiv page did not state a venue. Unverified.

## Q2. Published analysis of SWE-bench / Verified instances where visible or PASS_TO_PASS tests fail even with the gold patch, or the task requires changing existing tests

### Takeaway
Several analyses document noisy or incorrect test labels: OpenAI's Verified annotation, SWE-bench+, UTBoost, Epoch AI, and GitHub issues on gold-patch failures. Benchmark builders (SWE-bench-Live, TDD-Bench, test-evolution benchmarks) handle pre-existing, environment and flaky failures by *filtering instances out*, through before/after runs and repeated validation. None of these turn attribution into a skill the agent is scored on.

### Cited Findings
- **OpenAI, "Introducing SWE-bench Verified" (Aug 2024 per my memory; page returned 403 to my fetcher) [blog/vendor].** OpenAI annotated 1,699 random SWE-bench test samples and kept 500. One criterion asked whether the FAIL_TO_PASS tests reject valid solutions, scored on a 0–3 severity scale. Samples were removed if the problem statement or the FAIL_TO_PASS tests had issues. A widely repeated secondary figure says 68.3% of samples were filtered. That figure did not reconcile with 500/1,699 (≈70.6% removed) in the snippets I saw. — [OpenAI post](https://openai.com/index/introducing-swe-bench-verified/) (via search snippet); [secondary summary](https://www.longtermwiki.com/source/e1f512a932def9e2)
- **OpenAI, "Why we no longer evaluate SWE-bench Verified" (Feb 2026 per search snippet; 403 on fetch) [blog/vendor].** Says Verified is increasingly contaminated and recommends SWE-bench Pro. Notes that many valid solutions fail tests on import errors. — [OpenAI post](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/) (snippet only). A secondary blog claims OpenAI later found about 30% of SWE-bench Pro's 731 tasks broken. That claim is unverified. — [dev.to](https://dev.to/thegatewayguy/openai-just-found-30-of-swe-bench-pro-is-broken-and-retracted-their-own-recommendation-3nlh)
- **SWE-bench GitHub issue #267, "5 Instances in Verified Fail for Gold Patch" [issue tracker].** Five Verified instances (astropy, django) fail with the gold patch. The reporter attributes this to Verified not being updated. The same instances pass under the original princeton-nlp release. The issue is about two years old and its current status is unclear. — [GitHub #267](https://github.com/swe-bench/SWE-bench/issues/267)
- **SWE-smith issue #245 [issue tracker].** When a patched source file is also listed in PASS_TO_PASS, the gold evaluation restores that file and undoes the fix, so the gold patch is scored unresolved. This is a harness artefact that produces false "failures". — [SWE-smith #245](https://github.com/SWE-bench/SWE-smith/issues/245)
- **SWE-Bench+ (Aleithan et al.), arXiv 2410.06992, Oct 2024 [preprint; a York University repository copy exists].** Among patches marked resolved, 32.67% (33.47% in another version) had the solution leaked in the issue text. 31.08% (24.70% in a later version) were "suspicious" because weak tests passed incorrect or incomplete patches. SWE-Agent+GPT-4's rate fell from 12.47% to 3.97% after filtering. — [arXiv 2410.06992v2](https://arxiv.org/html/2410.06992v2)
- **UTBoost (Yu, Zhu, He, Kang), arXiv 2506.09289, ACL 2025 Long [peer-reviewed].** LLM-generated tests find insufficient test cases in 23/300 Lite and 26/500 Verified instances. The abstract says 36 instances and 345 erroneous patches labelled as passed. These corrections change 40.9% of Lite and 24.4% of Verified leaderboard entries, with 18 and 11 ranking changes. An improved log parser found **annotation errors in 54.6% (164/300) of Lite and 54.2% (271/500) of Verified instances**, meaning the original parser mislabelled test statuses. — [arXiv 2506.09289](https://arxiv.org/abs/2506.09289); [ACL Anthology PDF](https://preview.aclanthology.org/landing_page/2025.acl-long.189.pdf); [Kang Substack](https://ddkang.substack.com/p/swe-bench-verified-is-flawed-despite)
- **Epoch AI, "What skills does SWE-bench Verified evaluate?" [blog].** Estimates 5–10% of Verified instances are flawed. Notes that Verified uses only tests in the test-patch file(s), so regressions elsewhere in the suite are not caught. — [Epoch AI](https://epoch.ai/blog/what-skills-does-swe-bench-verified-evaluate)
- **SWE-bench-Live (Microsoft), arXiv 2505.23419, 29 May 2025 [preprint].** Collects per-test outcomes before and after the gold patch, with framework-specific log parsers. FAIL_TO_PASS means fail or error before and pass after. PASS_TO_PASS means pass both times. An instance needs at least one FAIL_TO_PASS. "Validation is repeated multiple times… Only instances with consistent results across all runs are retained." The number of reruns is not stated, and fail→fail tests are not discussed. — [arXiv 2505.23419](https://arxiv.org/html/2505.23419v1)
- **RepoLaunch follow-up, arXiv 2603.05026 (2026) [preprint].** Argues that building the repo is not enough and adds a management stage for rebuilds, re-tests and test-status tracking over time. — [arXiv 2603.05026](https://arxiv.org/html/2603.05026v1) (snippet)
- **TDD-Bench Verified, arXiv 2412.02883 (Dec 2024) [preprint].** Removed instances where tests failed because of the environment rather than the solution. On re-validation it dropped 7 instances whose environment could not be recreated, plus 44 lacking the expected fail-to-pass behaviour. — [arXiv 2412.02883](https://arxiv.org/pdf/2412.02883)
- **SWE-Factory, arXiv 2506.10954 (Jun 2025) [preprint].** Labels an instance fail2pass from the exit code (non-zero before, zero after). Documents a case where an ImportError crashed test collection, so *no tests ran*: an environment failure that looks like a test failure. — [arXiv 2506.10954](https://arxiv.org/pdf/2506.10954)

### Inferences
- UTBoost's ~54% parser-annotation-error rate means per-test pass/fail status scraped from logs is itself unreliable. Any attribution scheme that diffs test IDs across runs inherits this problem. This is my inference; UTBoost measured it for benchmark labels, not agent loops.
- "Tests that must change because the task changes behaviour" correspond to FAIL_TO_PASS tests whose test patch modifies existing tests. OpenAI's "tests reject valid solutions" criterion is the closest published annotation of this. I found no published count of Verified instances whose test patch edits pre-existing tests.

### Gaps
- I could not fetch OpenAI's two posts (403). The exact criteria wording and percentages are from search snippets only.
- No found source counts PASS_TO_PASS tests that fail with the gold patch across current Verified. Only the 5-instance GitHub report.
- SWE-rebench's flaky-test filtering: searched, but not found in the snippets.

## Q3. Flaky-test detection and regression-failure attribution in APR and LLM agents (plausible vs correct, overfitting)

### Takeaway
Classic APR research treats flaky and rotten tests as one cause of plausible-but-wrong patches, and usually *removes* flaky tests from benchmarks. In agent work, flakiness shows up as run-to-run evaluation variance. I found no peer-reviewed study of flaky-test handling *inside* an LLM agent's retry loop. The closest is a 2026 practitioner blog.

### Cited Findings
- **Code-removal patches study, Empirical Software Engineering (Springer), 2021 [peer-reviewed].** 11 of 52 builds with incorrect test-suite-adequate patches (21.15%) involved flaky tests. Argues that plausible patches are better explained by specific test-suite problems (rotten tests, buggy tests, flaky tests) than by weak suites alone. — [EMSE 10.1007/s10664-021-10100-7](https://link.springer.com/article/10.1007/s10664-021-10100-7)
- **"On the Impact of Flaky Tests in Automated Program Repair" (Qin et al.; ~2021; SANER per my memory, unverified).** Flaky tests can produce patches that look reasonable but are wrong. — [ResearchGate](https://www.researchgate.net/publication/348187542_On_the_Impact_of_Flaky_Tests_in_Automated_Program_Repair)
- **University of Luxembourg flaky-tests-in-APR paper (ORBilu 10993/50217) [peer-reviewed conference proceedings per repository label; title not confirmed].** Search snippet: flaky tests are rare (~0.3% of tests) but affect experiments for most Defects4J faults, and are usually removed from repair benchmarks. My fetch failed on a TLS error. — [ORBilu](https://orbilu.uni.lu/handle/10993/50217)
- **Patch overfitting magnitude, FSE 2024 companion (ACM 10.1145/3663529.3663776) [peer-reviewed].** Across 10 APR tools, overfitting "might not be as bad as previously thought". Earlier estimates were 70–98% overfitting. — [ACM DL](https://dl.acm.org/doi/10.1145/3663529.3663776)
- **Test-based patch clustering, arXiv 2207.11082 (2022) [later journal version on PMC].** Defines overfitting as passing all existing tests but failing other inputs, and clusters plausible patches by behaviour on generated tests. — [arXiv 2207.11082](https://arxiv.org/pdf/2207.11082)
- **Empirical review of Java APR tools (Durieux et al.), arXiv 1905.11973 (2019) [ESEC/FSE 2019 per my memory].** 2,141 bugs and 23,551 repair attempts. — [arXiv 1905.11973](https://arxiv.org/pdf/1905.11973)
- **"On Randomness in Agentic Evals" (Bjarnason, Silva, Monperrus), 2026 [preprint; summary only].** 60k SWE-bench trajectories. Single-run scores vary by up to 6 percentage points, and non-determinism persists even at temperature 0, including from environments. Recommends pass^k. — [search summary; primary not fetched](https://tianpan.co/blog/2026-07-02-flaky-tests-poison-agent-loops)
- **tianpan.co, "Flaky Tests Poison Agent Loops…", 2 Jul 2026 [blog, opinion].** Cites Google's ~1.5% flaky test-run rate. Argues that agents treat red results as ground truth and can learn to game noisy feedback. Recommends labelling quarantined tests as advisory and logging retries rather than retrying silently. — [blog](https://tianpan.co/blog/2026-07-02-flaky-tests-poison-agent-loops)
- **SWT-Bench (Mündler et al.), arXiv 2406.12952 (NeurIPS 2024 per my memory) [see link].** Requiring a self-generated test that *failed before* the fix and passes after more than doubles SWE-agent's precision on fixes. This is a fail-before/pass-after attribution filter applied to the agent's own tests. — [arXiv 2406.12952](https://arxiv.org/pdf/2406.12952)
- **CoHarden ("Beyond Fail-to-Pass"), arXiv 2607.19843, 22 Jul 2026 [preprint].** The in-trajectory F→P check "can pass even when both the generated patch and generated test are wrong". Hardens tests against mutation patches. Does not address flaky or pre-existing failures. — [arXiv 2607.19843](https://arxiv.org/abs/2607.19843)

### Inferences
- APR treats flakiness as a data-cleaning problem (quarantine or remove). Agent loops on live repos cannot pre-clean, so they need an online version: rerun a failure, or compare it against a baseline. I found this framed only in a blog, not in a measured study.

### Gaps
- Classic APR anchors I know of but did not fetch this session: Smith et al. "Is the cure worse than the disease?" (FSE 2015) and Qi et al. Kali / plausible patches (ISSTA 2015). They are not cited above as fetched sources.
- No primary fetch of the "On Randomness in Agentic Evals" paper.

## Q4. Work that frames "was this failure caused by my change?" as an agent decision and measures its accuracy or cost

### Takeaway
The nearest direct measurement is "Breaking, Stale, or Missing?" (May 2026 preprint). It scores whether agents can identify which *existing tests* a change obliges them to update, and finds identification F1 below 50% for all configurations. Agents over-predict, and stale tests (which still pass) are mostly missed because agents depend on an execute-fail-fix loop. FixedBench (2026) measures a related judgement: whether to act at all. TensorBench reports regression-only failures. I found no paper that measures an agent's accuracy at classifying a failing test as pre-existing/unrelated vs self-caused, or the cost of misclassifying.

### Cited Findings
- **"Breaking, Stale, or Missing? Benchmarking Coding Agents on Project-Level Test Evolution" (Shang, Zhang, Hu, Fang, Xiao, Chen), arXiv 2605.06125, 7 May 2026 [preprint].** Defines Test-Breaking (fails after the change, developer edits it), Test-Stale (still passes but the developer updates it) and Test-Missing (new test needed). Seven configurations, including Claude Code (47.1%) and Codex CLI (49.4%, the best), reach identification F1 of 45.7–49.4%. Best F1 by type: Breaking ≈60.7%, Stale ≈37.4%, Missing ≈54.3%. Recall exceeds precision by 9.1–17.8 points, i.e. agents over-flag tests. A heuristic baseline got 66.1% recall at 2.0% precision. The authors attribute Stale failures to a "reactive 'execute-fail-fix' loop" that "structurally cannot address stale or missing tests". Update composite score 63.6–72.3%; executability 87.7–99.2%. The dataset *excluded* commits with "pre-existing test failures unrelated to the commit's code changes". — [arXiv 2605.06125](https://arxiv.org/html/2605.06125v1)
- **FixedBench, "Coding Agents Don't Know When to Act", arXiv 2605.07769 (May 2026) [preprint].** State-of-the-art models propose undesirable changes in 35–65% of cases where no change is needed. — [arXiv 2605.07769](https://arxiv.org/html/2605.07769v1) (snippet)
- **TensorBench, arXiv 2606.05570 (Jun 2026) [preprint].** Classifies failed agent attempts by whether they broke pre-existing tests. In the "regression only" bucket, all agent-written tests pass but an existing test breaks. Codex 5.5 had 19 regression-only failures, the most of any agent. — [arXiv 2606.05570](https://arxiv.org/pdf/2606.05570) (snippet)
- **TDAD (2026):** naive TDD prompting *increased* regressions, from 6.08% to 9.94%. Targeted impacted-test context reduced them to 1.82%. This is a cost/benefit result for telling the agent which tests matter. — [arXiv 2603.17973](https://arxiv.org/abs/2603.17973)
- **Agentless (2024):** puts the "which tests will my fix legitimately change" decision in an LLM call but reports no accuracy for it. — [Agentless v2](https://arxiv.org/html/2407.01489v2)

### Inferences
- Taken together, the evidence suggests agents left to their own judgement both over-attribute (flagging tests as needing change that don't, per the precision gap) and under-detect (stale tests). This argues for a deterministic baseline diff (failing-before set vs failing-after set) as the primary signal, with LLM judgement reserved for tests that newly fail. That is my synthesis; no paper tests this combination head to head.
- The benchmarks above mostly *exclude* instances with pre-existing unrelated failures. So published agent scores are largely measured in conditions where this attribution problem has been engineered away. Real repos with red baselines are under-represented.

### Gaps
- Searched: "pre-existing test failures" / "already failing" with coding agents; flaky tests with SWE-bench and agents; AutoCodeRover/CodeR/OpenHands regression runs; APR flaky tests. I found **no** paper that (a) gives an agent a repo with a red baseline and measures whether it wrongly tries to fix, or wrongly blames itself for, the pre-existing failures, or (b) measures the token or iteration cost of misattribution in retry loops. Searches were limited to about 16 calls, so a more targeted sweep (ICSE/FSE 2026 proceedings, "test failure triage" + LLM, "regression attribution" + agent) may still find something.
- "How Coding Agents Fail Their Users" (arXiv 2605.29442, 20,574 sessions) and "Failure as a Process" (arXiv 2607.09510) came up in searches. They may contain qualitative evidence on agents mis-blaming test failures, but I did not read them. — [2605.29442](https://arxiv.org/pdf/2605.29442); [2607.09510](https://arxiv.org/pdf/2607.09510)
